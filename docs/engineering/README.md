# Engineering

Engineering documentation explains how the Atria frontend is structured, how it behaves, and how to
change it safely.

Atria is currently a client-only React application. There is no backend, API, database,
authentication, or persistence. Documents in this section describe the real implementation and mark
future direction clearly.

## Engineering principles in the current code

1. **Keep the surface small.** No state library, no data layer, no abstraction without a demonstrated
   need.
2. **Keep the visual system in CSS.** The design language is authored, not generated by a utility
   framework.
3. **Make routes explicit.** The route table is readable in one file.
4. **Be honest about placeholders.** Studio briefs state that they are placeholders.
5. **Verify with a build.** CI runs the production build on every push and pull request.
6. **Document structural decisions.** ADRs record tradeoffs.

---

## Current constraints

- No TypeScript.
- No linter or formatter configuration.
- No automated tests.
- No error boundary or loading states.
- No code splitting.
- No backend integration.
- `/docs` sits outside the router.
- Global CSS is shared across all pages.

These constraints are documented so contributors can improve them deliberately rather than discover
them by surprise.

---

## Making an engineering change

1. Read the relevant architecture document.
2. Check whether the change requires an ADR.
3. Keep the change focused and reversible.
4. Run `npm run build`.
5. Perform the manual checks in [Testing strategy](../quality/testing-strategy.md).
6. Update affected documentation in the same pull request.
